**High availability**: run LajurOps as several replicas behind a load balancer and upgrade without downtime,
with a ready-made `docker-compose.ha.yml`. Plus clear **"not found"** pages instead of silent redirects.
No database migrations. One new, optional setting (`SHUTDOWN_DELAY`).

## Run several replicas

The app keeps no state of its own (everything is in Postgres, sign-in is a Keycloak token on each request),
and now it's safe to run several copies:

- **Migrations are locked.** Replicas starting at the same time take turns: the first applies the migrations,
  the others wait and find nothing to do.
- **Reminders run on one replica at a time.** If that replica stops or crashes, another takes over within a
  minute. Nothing is sent twice.
- **`/readyz`** for load balancers: it also checks the database (503 when it's unreachable) and reports
  "shutting down" during shutdown. `/healthz` stays the liveness check.
- **Clean shutdown.** A stopping replica now finishes the requests in flight before it closes its database
  connections. Before, a rolling restart could cut off a few requests.
- **`SHUTDOWN_DELAY`** (e.g. `5s` on Kubernetes) keeps serving for a moment after SIGTERM, so the load
  balancer stops sending traffic first.

## docker-compose.ha.yml

A variant of `docker-compose.yml` that reads the same `.env`:

- the app as **3 replicas** (`LAJUROPS_REPLICAS`), each capped at `LAJUROPS_DB_POOL` (10) database connections;
- **nginx** in front (`deploy/nginx/lajurops-ha.conf`), which spreads requests over the replicas and retries
  another one when a replica is down;
- **`deploy/rolling-update.sh`** for upgrades without downtime: it starts the new version next to the old one,
  waits until each new replica is ready, then stops the old ones.

```bash
docker compose -f docker-compose.ha.yml up -d
LAJUROPS_VERSION=0.6.0 deploy/rolling-update.sh
```

This makes the app tier highly available on one Docker host. Postgres and Keycloak still run as single
containers in it; for a setup that survives losing a host, run them highly available too. The README's new
section "Running several replicas" covers this, connection pool sizing, and a Kubernetes example with probes.

| Tested | Result |
|---|---|
| 5 replicas migrating an empty database at once | each migration applied once, all started |
| 3 replicas behind nginx, restarted one by one under load | **0 failed** of 48,358 requests |
| `rolling-update.sh` replacing all 3 replicas under load | **0 failed** of 48,600 requests (23 s) |
| The replica running reminders killed | another took over in about 30 s |

## "Not found" instead of a silent redirect

- An address that isn't a page shows **Page not found**, with **Search** and **Go to your board**, instead
  of jumping to the first board.
- A workspace link that doesn't exist, or that you can't see, shows **Workspace not available** (ask an
  administrator for access). The server answers "not found" in both cases on purpose, so nobody can probe for
  other teams' workspaces.
- A mistyped view (`/w/<id>/timelin`) goes to the board and fixes the address bar.
- The server now answers unknown addresses (and missing asset files) with **HTTP 404**, for proxies and
  monitoring.
- Errors like "not found" or "not allowed" are no longer retried, so they show at once.
